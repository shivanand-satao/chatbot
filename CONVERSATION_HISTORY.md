# Conversation history contract and context baseline

## Implemented offline

`conversation_context.py` defines immutable validated owner, conversation, message, and summary records plus an ownership check and bounded context builder. It performs no authentication, database reads/writes, model calls, or persistent storage.

- Ownership is `(account_kind, account_id)`, keeping the user/admin namespaces separate. An admin does not bypass ownership checks. Owner values must come from verified server identity, never a client-supplied claim.
- Each message references exactly one conversation, with a positive sequence number, user/assistant role, bounded nonempty content, and complete/pending/failed status. No system/tool message role is accepted in saved user-facing history by this baseline.
- The builder accepts one bounded contiguous ascending history page from trusted server storage, ending with the saved current user question. Foreign conversation messages, duplicates, gaps, and reversed order are rejected.
- Context includes a contiguous recent suffix of complete messages within character and message limits. An oversized or incomplete older message stops expansion instead of silently skipping to older turns. The current question must fit; it is never silently discarded or truncated.
- Optional summaries are supplied by trusted storage, not generated by this helper. They must match conversation identity/revision and precede the current question. A summary is included only when its covered boundary joins exactly to the selected suffix and fits the budget. It is explicitly labeled derived/unverified.
- The caller receives included sequence numbers, summary usage, omitted-history information, and warnings. User and assistant contents remain distinct JSON fields. JSON encoding is not protection against all prompt injection; the eventual generator must treat history as untrusted context rather than privileged instructions.

History is not evidence. Follow-up questions still require fresh database/document retrieval. This module does not rewrite follow-ups, infer intent, prove old answers correct, or merge prior conversations. Character limits are not model token budgets.

## Persistence and returning-user behavior still pending

No chats are saved across restarts or visits yet. No migrations, storage repository, history API, or frontend history UI were added here.

The next persistence stage must implement:

1. Reviewed conversation/message/source migrations in the chatbot schema, with ownership, sequence, idempotency, size, and deletion constraints.
2. Controlled storage operations with server-side owner checks on every read/write/delete; never reuse the generated-query execution path for writes.
3. Server-to-server authentication integration with the existing backend and explicit account-role/namespace validation.
4. Cursor-paginated history, conversation listing, New chat, resume-last-active behavior, deletion, and retry states.
5. Stable sequencing and request idempotency; serialize or reject concurrent turns; avoid holding transactions during external model calls.
6. Revision semantics: update the conversation revision on history mutations that invalidate a stored summary, and regenerate/replace summaries with a covered-turn boundary. Define how pagination joins summaries without missing or duplicated turns.
7. Timestamps, evidence provenance, failure records, retention/deletion policy, account-switch cancellation, and stale-response prevention.
8. Runtime database isolation tests, return-after-login tests, and frontend integration before claiming persistent chat support.

This baseline expects the server to provide its complete selected page, including failed/pending turn records. Storage must not pre-filter those records in a way that silently changes continuity. Runtime models should use token-aware limits for the complete prompt, reserving space for new evidence, instructions, and output.
